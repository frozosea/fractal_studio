# AI 辅助分形探索经验与工作流

最后更新：2026-08-09（Codex 初稿；Claude 补充实测部分；Studio AI 开发复核）

## 1. 文档目的

这份文档用于指导后续 AI agent 辅助用户探索、筛选并发布分形作品。当前目标是沉淀已经验证过的工作方法，**不是立即开发新的 agent、编排框架或自动化基础设施**。

规划中的四项核心能力是：

1. **找位置**：根据视觉意图寻找值得观察的坐标、尺度、特殊点和公式区域。
2. **调色**：在结构正确的前提下，用有限的、有目的的配色变体强化主题和层次。
3. **微调与构图**：围绕候选位置微调中心、尺度、旋转和画幅，形成可发布的构图。
4. **写文案并上架**：基于真实配方和最终图像生成标题、说明、标签与商品草稿，通过质量门后再发布。

AI 的定位应是“探索副驾驶”：擅长扩大搜索范围、记录参数、批量比较和排除明显失败；用户负责最终的审美判断、品牌判断与发布确认。除非用户明确授权，agent 不应把“生成成功”理解为“允许公开上架”。

## 2. 总体原则

### 2.1 图像是最终证据

数学属性只能缩小搜索范围，不能代替视觉验收。周期为 5、具有五重对称或位于某个特殊点附近，都不等于画面中必然出现清晰、分离的五角星；四重卫星结构也不等于自然形成符合预期的卍形。

因此，每个候选都必须经历：参数推导、低成本预览、视觉检查和结果记录。搜索器返回的是候选，渲染图才是判断依据。

### 2.2 一次只改变一类变量

位置、尺度、旋转、计算模式和配色同时变化时，无法判断改进来自哪里，也难以复现。推荐顺序是：

```text
结构位置 -> 观察尺度 -> 构图 -> 数值/染色模式 -> 调色板 -> 发布文案
```

用户只要求重新染色时，应保留坐标、尺度和公式；用户只要求构图微调时，不应顺手更换公式或目标结构。

### 2.3 精确配方与图像同等重要

每张候选图都要保存可复现的 canonical spec，而不能只保存 PNG。深度缩放必须保留 `centerReStr`、`centerImStr` 等完整精度字符串；double 形式的坐标只适合显示或浅层预览。特殊点、高精度与 perturbation 路径的具体约定见 [Special Points / 特殊点链路](special_points.md) 和 [Render Pipeline / 二维渲染链路](render_pipeline.md)。

### 2.4 少量、有解释的候选优于盲目堆图

一轮建议提供 3–8 个有明显区别的候选，并给出变化轴和推荐理由。agent 应先过滤明显空白、失焦、结构错误、过曝或缩略图不可读的结果，不应把几十张未经筛选的图片交给用户。

### 2.5 用联系表审阅，不要逐张审阅

实测中最能提高探索吞吐的一条：把一轮 12–20 个候选**拼成一张带标签的联系表**再看，而不是一张张翻。理由不只是省时间——并排比较才看得出"这一版比那一版好在哪"，逐张看只能判断"能不能用"。

具体做法：固定单元格尺寸，每格左上角压候选 ID、底部压变化轴的取值（如 `bail_1.2`、`1.0e-12`），失败的格子也保留并标 FAILED，这样一眼能看出参数扫描在哪一段塌掉。扫描 `bailout`、`cyclesPerOctave`、`theta` 这类单参数时，按取值顺序排列，联系表本身就是一条响应曲线。

需要定配色或判细节时再单独看大图，并且要看母版而不是预览（见 9.8、9.9）。

### 2.6 草稿、私有作品与已发布商品必须分离

探索结果默认保持私有或草稿状态。错误候选、过渡产物和被否决的标题不得留在市场中。配方、渲染资产、作品记录、listing 和发布状态是不同对象；自动化操作要逐项核对，且使用幂等键避免重复创建或重复上架。

## 3. 标准探索流程

```text
视觉意图
  -> 提取硬约束与软偏好
  -> 粗搜索位置和数量级
  -> 生成带索引的预览矩阵
  -> 筛选结构候选
  -> 调色矩阵
  -> 构图微调
  -> 高分辨率私有渲染
  -> 质量检查
  -> 文案与 listing 草稿
  -> 用户确认
  -> 发布并回查市场展示
```

推荐的单轮规模：

- 粗搜索 8–24 个低成本候选；
- 收敛到 3–6 个结构候选；
- 对最佳结构生成 4–8 个配色方案；
- 对最佳配色生成 3–9 个构图微调；
- 最终只高分辨率渲染 1–3 个版本。

这些数字是经验默认值，不是硬限制。目标明确时可以缩减；探索全新公式或 transition 区域时可以分批扩大，但每轮都要记录结论。

## 4. 功能一：帮忙找位置

### 4.1 先把自然语言转成约束

agent 开始搜索前，应将描述拆成两类：

- **硬约束**：公式族、Mandelbrot 或 Julia、是否要求 Mandelbrot 内嵌 Julia、主体数量、主体是否分离、主体必须位于小 Mandelbrot 周围、目标画幅等。
- **软偏好**：像山脉、深海、金属、红底黄星、画面疏密、中心或偏心构图等。

例如，“很多互不相连的五角星，红底黄星，而且希望在 Mandelbrot 里的 Julia 区域寻找”至少包含三项不可互换的硬约束：五角星轮廓、视觉上分离、Mandelbrot 内嵌 Julia。找到五重花瓣、五向辐射或直接 Julia 都不能标记为成功。

### 4.2 使用由粗到细的搜索金字塔

1. 从已知锚点、特殊点、mini-Mandelbrot 或用户给出的近似坐标开始。
2. 在对数尺度上扫视野，而不是只做线性微调。
3. 在每个尺度周围做小范围中心网格或低差异采样。
4. 只对视觉上接近目标的区域提高迭代数和精度。
5. 给每张预览附上候选 ID，保持图片与参数一一对应。

特殊点搜索时要检查 `accepted`、`actual.period`、residual 和 primitive/satellite 关系，不能只看 Newton 是否 `converged`。若目标是某个父周期之外的嵌套结构，还应排除仅仅落回父周期倍数的候选。

### 4.3 深缩放的尺度经验

深层 mini-Mandelbrot 的 nucleus 或 component 尺寸通常不是完整视觉结构的观察尺度。过度贴近 nucleus 容易只看到局部丝状物；拉远若干数量级后，才可能看出一圈 satellite 或内嵌 Julia 的整体组织。

实践中可以把“约几十倍 component 尺寸观察中心结构、约上千倍观察更完整邻域”作为起始启发式，但不能当公式使用。不同周期和区域差异很大，必须做对数尺度 sweep，并以预览判断。

深 zoom 中要从搜索到渲染全程传递精确十进制字符串，并选择 fp128/MPFR/perturbation 等可用高精度路径；否则坐标在进入渲染器前就可能被 double 舍入到错误位置。

**实测：能潜多深由锚点的有效位数决定，不由求解器决定。** 用一个 33 位有效数字的锚点做尺度扫描，1e-24、1e-28、1e-30 都干净利落且细节持续展开，而 1e-33 及更深整片空白——位数用尽之后，"放大"实际是在放大一个不在边界上的点。所以想再深一档，要先解出更高精度的坐标，而不是调渲染参数。

同一轮实测的两项配套事实：

- 引擎实际走的是微扰路径。`GET /compute/v1/runs/{runId}` 返回的 `hardwareExecution.actualScalar` 是 `perturb-mpfr158-fp64`（158 位 MPFR 参考轨道 + fp64 逐像素偏移），CUDA 执行。它不会随深度逐渐劣化，要么正常要么位数耗尽。Platform 侧保存的 `compute_result_json` 只有 artifacts，取精度证据必须直接问 Compute。
- 迭代预算随深度独立增长，且是另一个会先撞上的上限。经验量级：1e-12 约 8k，1e-18 约 20k，1e-24 约 60k，1e-30 约 120k。预算不足的表现和精度耗尽**完全一样**（整片内部色），排查时要先加迭代再怀疑坐标。

### 4.4 位置助手的理想输出

每次返回一个经过排序的候选表：

| 字段 | 含义 |
|---|---|
| `candidateId` | 本轮稳定编号，与预览图一致。 |
| `centerReStr` / `centerImStr` | 可复现的精确中心。 |
| `scale` | 视野尺度及其含义。 |
| `source` | 已知锚点、特殊点求解、网格扫描或人工种子。 |
| `mathEvidence` | 周期、前周期、残差、兼容公式等数学依据。 |
| `visualObservation` | 实际看到的主体数量、连通性和构图。 |
| `constraintMatch` | 满足和未满足哪些用户约束。 |
| `nextAction` | 淘汰、继续缩放、平移或进入调色。 |

不要用数学证据替代 `visualObservation`，也不要为接近但不符合的形状起一个误导性标题。

### 4.5 自动导航与形状评分器（实测）

**手工猜坐标再直接深缩放几乎必然失败。** 实测中，按记忆或文献写下一个"著名坐标"，然后把 `scale` 直接调到 1e-3 以下，得到的往往是整片纯色——落点偏离边界哪怕极小，视野内也只剩内部或快速逃逸区。可靠做法是**逐级下潜**，每一步都用图像确认还站在结构上：

```text
渲染当前视野 -> 切 N×N 网格 -> 给每格打分 -> 选最高格重新居中 -> 缩放一档 -> 重复
```

每步同时按比例提高 `iterations`；若使用 `colorProgram`，要同步放大 `cycles` 以保持 band 不变（见 5.4）。

**评分函数决定它走到哪里，这是这个方法的全部难点。**

- **纯边缘能量会走进噪声。** 第一版评分器取梯度均值，结果每次都停在混沌细丝区——那里边缘统计最高，构图却最差。
- **改成"细节覆盖率窗口"后才可用。** 统计强边缘像素占比，只有落在约 `8%–35%` 时给满分，过低（空白）和过高（噪声）都衰减。这个区间对应的正是"干净背景上有装饰"的经典构图。同时要求灰度标准差有下限，排除单色画面。

**目标形状可以直接写成评分函数。** 寻找卍形时用的判据是"四分之一转对称但不镜像对称"——手性正是卍与十字、四瓣花的区别：

```text
score = corr(img, rot90(img)) - max(corr(img, fliplr(img)), corr(img, flipud(img)))
```

两点实测经验：一是**必须裁中心再算**，整幅图打分会被四周的背景场稀释，而锚点附近的背景场本身常常近似镜像对称；二是**这个分数只能筛选，不能定案**，最终仍要看图——高分候选里既有卍形，也有旋转对称的花瓣。

**诚实的能力边界**：自动下潜器是侦察兵，不是画师。它倾向沿边界横向行走，容易停在斜切画面的边界线上，而不会把螺旋放正居中。实测中它的产出质量稳定低于已知的经典坐标，适合用来开辟新区域和批量生成候选，不适合直接交付。

## 5. 功能二：帮忙调色

### 5.1 先确认结构，再调色

调色可以突出层次、隐藏噪声或改变氛围，但无法把七向辐射变成五角星，也无法让错误坐标变成正确构图。结构未通过时，应返回位置搜索，而不是继续用色彩掩盖问题。

建议先用灰度、中性或结构清晰的内置 palette 检查几何，然后再构造少量命名清楚的配色方案，例如“朱红—金黄低频”“深蓝—金色高对比”“地形图层级色”。

### 5.2 分开控制染色变量

建议按以下顺序调整：

1. 数值 field / metric 与 `smooth`；
2. `colorMode`；
3. palette 或 `colorProgram` stops；
4. `cyclesPerOctave` 或 `cycles`；
5. `phase`；
6. interior / invalid color。

`eq_full` 搭配内置 palette 通常适合先观察全局层次。深缩放中，较低的 `cyclesPerOctave` 往往能形成更平静、连续的宽色带；`0.025–0.12` 可作为试探区间，但不是统一答案。

自定义 `colorProgram` v1 当前只支持 `colorMode=direct`，不能假定它能复刻 equalized 模式。自定义色带的输入语义、范围和限制以 [Coloring Contract / 染色合同](coloring_contract.md) 为准。遇到画面全灰、色带挤在一端或颜色完全不出现时，应该检查原始 field 分布或做参数 sweep，不能凭感觉反复猜 stop 阈值。

### 5.3 同时检查大图与缩略图

市场作品首先以缩略图被看到。最终配色至少检查：

- 主体是否从背景中分离；
- 暗部是否仍有细节；
- 高光是否吞掉丝状结构；
- 缩略图是否仍能辨认主题；
- 水印或 UI 覆盖是否妨碍判断；
- 放大后是否出现色带断层或过度噪声。

调色助手的输出应包含联系表（contact sheet）、palette 参数和一句差异说明，而不只是若干无名 PNG。

### 5.4 染色输入的实测数学

5.2 给出了调整顺序，但只要读一次着色器就能把这些参数从"凭感觉试"变成"可预测"。以下映射来自 `backend/src/compute/colorize.cpp` 与 `color_program.cpp`，并经渲染验证。

**escape metric + `colorProgram`**：

```text
input = (iter + 1) / (iterations + 2)
value = wrap(input * cycles + phase)
```

推论是**决定观感的是 `band = iterations / cycles`（每个色环覆盖多少次迭代），而不是 `cycles` 本身**。这条极其实用：

- 想加迭代数换取细节时，必须**同比例放大 `cycles`**，否则整幅图会向色带起点压缩、明显变暗。
- 反过来，只要 band 不变，同一套配色在 600 次和 60000 次迭代下观感一致——深缩放系列因此可以共用一个调色方案。
- 深缩放要用大 band（数百到数千），浅视野用小 band（10–40）。band 太小时细丝会走样成噪点。

**非 escape metric（`min_abs` / `envelope` / `max_abs` 等）+ `colorProgram`**：

```text
input = min(1, raw_field / bailout)
```

推论是**`bailout` 在连续场里是亮度旋钮，不只是逃逸阈值**。实测扫描：`0.6` 主体缩成一点，`1.0–1.6` 是甜区（整个场被推上色阶，出现体积感和光泽），`2.0–3.0` 正常，超过 `10` 全部塌进色带暗端。同一个视角、同一个度量，只改 bailout 就能得到两件不同的作品。

**均衡模式的两条硬限制**：

- `eq_full` / `eq_center` **仅对 escape metric 生效**，其它 metric 会静默走 direct 分支；
- 均衡模式下集合内部按 interior 色输出，内置 palette 是白色。因此**宽视野下大片白色内部会吃掉画面**，均衡配色实际只在内部占比小的深缩放里成立。

**`orbitProgram` 只能配 escape metric。** 与 `min_abs` 等连续场组合时返回裸 `502 compute_error`，不是校验错误——看起来像渲染崩溃，实际是不支持。这条卡住了 Newton/Nova 一类公式：它们的轨道收敛不逃逸，escape metric 下全部撞迭代上限、判为内部而输出空白，又无法改用连续场区分收敛盆，在当前引擎下画不出来。

## 6. 功能三：微调与构图

### 6.1 参数的职责

- `centerRe/centerIm`：改变取景，不应大到丢失主体；
- `scale`：控制主体大小、重复密度和呼吸空间，适合几何级数变化；
- rotation：在位置与尺度稳定后再调，避免旋转掩盖取景问题；
- aspect ratio：会改变最终裁切，搜索预览与成品画幅都必须检查；
- iterations / precision：保证细节可信，不是构图工具。

微调通常从基准配方出发，平移量使用视野宽高的一小部分，scale 采用相邻的几何比例。每个候选都记录相对基准的 delta，确保用户选中后能准确还原。

### 6.2 构图检查项

- 主视觉是否明确，第一眼能否找到；
- 重要分支、星角或旋臂是否被裁掉；
- 重复结构的数量和疏密是否服务主题；
- 是否有过大的空白 bulb 或无意义的噪声区；
- 主体居中、偏心或对角线布局是否有意图；
- 在最终市场卡片比例下是否仍成立；
- “放大”和“移动”是否被分别展示和解释。

寻找 motif 时可以用方形预览提高比较效率，但发布前必须按目标输出比例重新检查。构图助手应输出基准图与变体矩阵，而不是把用户带到一个无法回退的新状态。

### 6.3 把用户反馈转成下一轮硬约束

“不像”“还是连起来了”“配色不对”不能只作为闲聊记录。下一轮应将其改写为机器可检查的约束，例如：

- 主体必须是四向结构，并围绕可辨认的小 Mandelbrot；
- 星形应在画面中出现多次，且视觉上彼此分离；
- 背景以红色为主，主体以黄色为主；
- 只接受 Mandelbrot 中的内嵌 Julia，不接受直接 Julia 替代；
- 只改 palette，不改当前坐标与构图。

## 7. 功能四：自动写文案与上架

### 7.1 先验收作品，再写故事

标题、说明和标签必须来自最终配方与最终图像，不能反过来用文案包装未达标候选。五重对称的花瓣可以描述为“五重放射”或“五瓣结构”，不能因为目标曾是五角星就直接写成“五角星”。数学属性也应只写系统实际验证过的内容。

文案可以包含：

- 作品使用的公式或变体；
- 特殊点、周期或 transition 的可靠信息；
- 视觉主体、配色与氛围；
- 适合的展示场景；
- 诚实且克制的创作过程说明。

避免虚构数学结论、夸大稀有性，以及暴露账号密码、API key、服务地址中的秘密参数或内部调试信息。

### 7.2 默认创建草稿

自动化顺序应为：

1. 确认 creator 身份和创建/上架权限；
2. 确认 canonical recipe 已冻结；
3. 确认高分辨率 asset 及其 derivative 可访问；
4. 生成标题、说明、标签、价格和许可建议；
5. 创建私有作品或 listing 草稿；
6. 展示最终预览与元数据供用户确认；
7. 获得发布授权后改变发布状态；
8. 回查市场卡片、详情页、作者、价格、预览与购买状态。

即使用户授权 agent 批量发布，也应为每个作品执行自动 QA，并保留可撤回、可追踪的操作记录。重试必须依赖幂等键或查询已有对象，不能重复生成商品。

### 7.3 批量铺货时的实测约束

**listing 没有删除接口。** 只有 `publish` / `unpublish` / `PATCH`，且 `ListingUpdateInput` 不含 `assetId`。这意味着**草稿一旦指错资产就无法通过 API 纠正**——软删资产只会连带下架 listing，留下一条指向已删资产的记录。所以要先验收母版、再建 listing，顺序不能反。（本轮确实遇到一次，最后是直接改库把 `listings.asset_id` 指到新资产；这属于开发环境的补救，不是可推荐做法。）

**多创作者铺货要给每个账号一个明确的创作定位**，否则市场看起来是一个人换了几种心情。实测有效的分法是按"方法"而不是按"题材"：深潜、自定义公式、极简、均衡饱和、生物形态——每个定位对应一组固定的技术参数，产出天然自洽。

**跨账号不要复用坐标。** 同一个视角换配色挂在两个卖家名下，在市场里读起来是抄袭而不是致敬。铺第二个账号前先把已用坐标列出来避开。

**权限与流程的实测顺序**：注册后账号无任何角色，`creator` 角色由 `PATCH /v1/me/creator-profile` 授予，**且该调用会轮换 session token**（新 token 在 `X-Session-Token` 响应头，bearer 模式下必须接住，否则后续请求全部 401）。发布走 `POST /v1/listings/{id}/publish`，需要 `creator` 角色 + 幂等键。

## 9. 已验证的失败模式

### 9.1 对称性不是具象轮廓

本轮探索中，周期点与 multiplier 角度成功找到五重结构，但多次得到五瓣花、五向射线或相连的链状结构，而不是多个分离的五角星。结论是：周期和内部角是强搜索线索，不是视觉形状证明。

### 9.2 数学不连通不等于肉眼分离

一些 Julia 集从拓扑意义上可以是不连通的，但在当前分辨率、尺度和配色下仍表现为连续的 Z 形链或密集细丝。验收约束若是“看起来分开”，就必须按最终图像判断。

### 9.3 直接 Julia 不能替代 Mandelbrot 内嵌 Julia

两者可以共享局部动力学特征，但外部结构和构图语境不同。用户指定内嵌 Julia 时，直接 Julia 最多作为侦察工具，不能作为交付结果。

### 9.4 错误尺度会隐藏正确区域

只盯着 component 尺度容易错过完整 satellite 环或内嵌结构；拉得过远又会淹没目标。深层探索必须进行跨数量级的尺度比较。

### 9.5 配色不能补救错误几何

不正确的结构即使经过强烈红黄配色，也不会自动变成“五角星”或“卍形”。反复调色前应先通过灰度结构验收。

### 9.6 过早发布会污染市场

候选名称一旦暗示了未实现的视觉目标，市场就会出现“标题正确、图像错误”的商品。探索阶段保持私有，只有图像、文案和配方同时通过检查后才发布。

### 9.7 同时改太多参数会丢失因果

坐标、scale、palette、metric 一起变化虽然可能偶然产生好图，却很难知道如何继续微调，也难以建立可复用经验。候选矩阵应明确每一轴在改变什么。

### 9.8 预览与导出不是同一张图（实测，代价最大的一次）

`map_preview_v1` 当前把 `iterations` 截断到 `PREVIEW_MAX_ITERATIONS = 512`，而 durable render 用配方原值。历史实现不调整 `colorProgram.cycles`，曾导致预览与导出明显错色。2026-08-09 起，预览映射只在请求副本中按精确分母比例
`(previewIterations + 2) / (masterIterations + 2)` 自动缩放 escape `colorProgram.cycles`；canonical spec 与 durable render 不变。

这一条曾让一件作品带着错误配色进入草稿，直到对比母版才发现。两种可靠处理：

- 手工或其它旧客户端若绕过当前 Platform 映射，仍必须自行保持相同的 band；
- 正常 Studio 预览不要再次手工补偿 cycles，否则会发生双重校正。发布前仍要用母版验收，因为 512 次低成本预览不能证明高迭代细节与最终分辨率效果。

推广的结论是：**预览端点的任何"为交互性能做的限流"都可能让预览失真。** 验收必须以导出母版（或母版的缩略图）为准，用预览做筛选、用母版做验收。

### 9.9 缩略图会掩盖深缩放的真实明暗

同一份配方，576px 预览呈平滑的中间调，3072px 母版却明显更暗。原因是低分辨率下每个像素随机落在某个迭代值上，大量明暗像素被平均成中间调；分辨率提高后真实的精细结构解析出来，而这些结构大多落在色带暗端。

因此深缩放的配色**必须在接近成品的分辨率上判断**，或直接用母版缩略图做联系表。用 384px 预览拼的联系表适合比较构图，不适合定配色。

### 9.10 空白画面有三个不同病因，不要只改一个

渲染出整片纯色时，至少要分清：坐标偏离边界（下潜或改坐标）、迭代预算不足（加迭代）、锚点位数耗尽（换更高精度坐标）。三者表现完全相同，盲目调其中一个会浪费整轮。另有第四种：公式本身不逃逸（如 Newton/Nova），这时任何参数都救不了，见 5.4。

### 9.11 自动评分器会优化到你没要求的东西

用边缘能量当"细节"评分，搜索器会稳定收敛到混沌噪声区——那里确实边缘最多。评分函数写的是什么，它就找什么，不是"好看"。可用的做法是把审美约束显式写进去（覆盖率窗口、手性、对称性），并且**始终保留人工看图这一步**：分数用来排序候选，不用来替代验收。详见 4.5。

### 9.12 公开 API 名不等于数学名（本轮真实事故）

`backend/src/compute/variants.hpp` 里，公开 variant 名和它实际计算的分形有一半对不上：
`celtic` 算的是 Perpendicular Burning Ship，`buffalo` 算的是 Celtic，`celtic_ship` 算的
是 Buffalo，`mandelceltic` 算的是 Perpendicular Buffalo，`perp_ship` 算的是 Perpendicular
Celtic。源码里的别名注释直接写明了这层错位。

本轮**照 API 名推断公式**，写出了十条错误的商品说明——例如把 `buffalo`（实为 Celtic，
平方后只折实部）说成"实部虚部同时取绝对值"，把 `heart`（实为 Perpendicular Mandelbrot，
折实部并翻转虚部）说成"只折叠虚部"。这些描述读起来专业、语气笃定，但数学是错的，而且
错得不容易被发现——图是对的，只有文字错。全部十条都还在草稿阶段时被发现并改正，没有
流到已发布商品。

三条教训：

- **变体名是标识符，不是数学陈述。** 要讲公式必须回源码查迭代式，不能从名字推断。
- **写文案时"听起来专业"和"正确"是两个独立维度**，前者不蕴含后者。越流畅的错误描述
  越难被发现。
- 这类错误只能靠**核对源码**发现，渲染图、联系表、质量门里的视觉检查全都拦不住它。
  凡是文案里出现公式、周期、对称阶数这类可证伪的断言，都要有明确出处。

对照表见技能文件 `.claude/skills/fractal-exploration/references/variants.md`。

## 10. 质量门与职责边界

发布前至少检查以下七项：

| 检查项 | 通过条件 |
|---|---|
| 数学正确性 | 公式、坐标、特殊点/周期描述可验证。 |
| 视觉约束 | 主体形状、数量、连通性符合用户明确要求。 |
| 色彩可读性 | 大图和缩略图都有层次，无明显灰泥、过曝或色带故障。 |
| 构图 | 主体明确、裁切合理、画幅适配市场展示。 |
| 可复现性 | exact coordinates、scale、渲染与染色参数完整保存。 |
| 元数据诚实性 | 标题和文案没有把“相似”写成“已经实现”。 |
| 发布状态 | creator、asset、listing、权限、价格和公开状态均正确。 |

agent 可以自动淘汰技术失败和明显不符合硬约束的候选；主观审美相近的候选应交给用户选择。agent 不应自行修改数据库会员资格、绕过权限或使用明文凭证；需要测试身份时，应通过项目既有的管理与密钥机制。

补充一条实测背景，以免这条规则被误读成"做不到"：**会员资格目前没有自助路径**——`POST /v1/internal/membership/grant` 要求 `finance_operator` 角色，普通 creator 拿不到；`POST /v1/membership/checkout` 会走支付宝真实下单。因此在开发环境铺货时，用户可能明确要求直接向 `memberships` 表插入记录。这种情况下的正确做法是：照做，但**在会话与文档中明确记录"这是用户指示下的开发环境捷径"**，不要把它写进任何可复用的自动化脚本，也不要在没有明确指示时自行这么做。生产环境应补一条受控的授予路径，而不是依赖这个缺口。

## 11. 后续 agent 的最小能力接口

本文不规定实现技术，但四项功能的输出边界应尽量稳定：

1. **Location Finder**：输入视觉意图和当前视野，输出带理由、精确坐标和预览的排序候选。
2. **Color Assistant**：输入冻结的结构 spec，输出 4–8 个带参数与差异说明的配色变体。
3. **Composition Refiner**：输入基准 spec，输出带 center/scale/rotation delta 的构图矩阵。
4. **Listing Assistant**：输入已验收的作品与 creator 上下文，输出诚实文案、listing 草稿和发布前检查结果。

各功能都应读取并追加同一份候选 ledger，避免在阶段切换时丢失精度、用户否决理由或发布状态。

## 12. 衡量辅助探索是否有效

后续评估 agent 时，建议关注：

- 从用户描述到首个“有希望候选”的时间；
- 每轮候选的人工接受率；
- 从预览到最终发布的比例；
- 用户对位置、配色、构图和文案分别修改了多少；
- 同一 canonical spec 能否稳定复现；
- 因形状误判、文案失真或重复上架产生的返工次数；
- 已发布后需要撤回或修正的比例。

核心目标不是让 agent 生成更多图片，而是用更少的无效渲染，更快找到符合意图、可复现、可诚实描述并值得发布的作品。

## 13. 实测常量速查

以下数值来自 2026-07-29/30 对运行中的 dev 环境的实测与源码核对，随实现变动会失效；使用前建议重新验证一次，验证入口写在备注列。

| 项 | 实测值 | 备注 |
|---|---|---|
| 预览迭代上限 | `512` | `PREVIEW_MAX_ITERATIONS`，`compute_request_mapper.py`。导出不受此限，见 9.8。 |
| 预览尺寸上限 | `1024 × 1024`，且总像素 ≤ `1048576` | `preview_max_*` 设置项。 |
| 预览频率限制 | 30 次 / 分钟 | Redis 计数，超限返回 429。 |
| 并发导出上限 | 3 | `render_quota_max_active`，超出返回 429。 |
| 免费导出额度 | 20 张（终身） | `render_free_export_limit`；会员不计量。 |
| 导出尺寸上限 | `4096 × 4096`（image） | `ImageOutputSpec`。 |
| escape 色带输入 | `(iter+1)/(iterations+2)` | 不变量是 `band = iterations/cycles`，见 5.4。 |
| 连续场色带输入 | `min(1, raw/bailout)` | `bailout` 是亮度旋钮，甜区 `1.0–1.6`。 |
| `colorProgram` stops | 2–16 个，首 0 末 1 严格递增 | 且必须 `colorMode=direct`、不能与 `colorMap` 同时给。 |
| `cycles` 范围 | `(0, 256]` | 深缩放常用 band 数百至数千。 |
| 深缩放标量 | `perturb-mpfr158-fp64` | 158 位参考轨道 + fp64 偏移，CUDA。 |
| 深缩放深度上限 | 由锚点有效位数决定 | 33 位 → 约 `1e-30`；1e-33 起空白。 |
| 迭代预算量级 | 1e-12≈8k，1e-18≈20k，1e-24≈60k，1e-30≈120k | 与精度上限是两个独立瓶颈。 |
| `orbitProgram` 兼容性 | 仅 `metric=escape` | 否则裸 `502 compute_error`。 |
| axis transition 兼容性 | `escape` / `min_abs` / `max_abs` / `envelope`；拒绝 julia 与 orbitProgram | `min_abs` 才有光晕，escape 下近似剪影。 |
| 均衡模式兼容性 | 仅 escape metric；内部按 interior 色输出 | 宽视野下大片白色内部，见 5.4。 |
| DSL 上限 | `source` ≤ 4096 字符，参数 ≤ 32 个 | 支持分数次幂（取主支，负实轴有分支割线）。 |
| 精度证据接口 | `GET /compute/v1/runs/{runId}` | Platform 的 `compute_result_json` 只存 artifacts。 |
